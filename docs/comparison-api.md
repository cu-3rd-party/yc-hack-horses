# Сравнение полевого снимка

Контракт Go-ноды для рабочего режима Electron. Примеры используют короткие ID для читаемости. При включённой документации (`api.docs_enabled`) схема доступна на ноде по адресу `/api/scalar/openapi.yaml`. Типы запросов и ответов находятся в `packages/contracts/src/comparison.ts`. Пути ниже начинаются с `/api/v1`.

## Анализ

1. `POST /blobs` с `multipart/form-data`, поле `file` содержит байты оригинала. При первой загрузке нода отвечает 201, при повторной — 200. Клиент использует `sha256` из ответа. Получить оригинал можно через `GET /blobs/{sha256}`.
2. `POST /comparisons` принимает, например, `{"blob_sha256":"<sha256>","top_k":5}`. По умолчанию запрашиваем до пяти разных особей на каждую найденную лошадь.
3. Когда анализ готов, ответ 201 содержит общий снимок и все детекции. Индексы на экране начинаются с единицы, решения адресуются по стабильному `detection_id`.

```json
{
  "comparison_id": "cmp_42",
  "blob_sha256": "<sha256>",
  "detections": [{
    "detection_id": "d_1",
    "detection_confidence": 0.98,
    "annotation": {
      "horse_polygon": [[0.1,0.24],[0.42,0.31],[0.38,0.79],[0.14,0.75]],
      "traits": [{"key":"muzzle","value":"light","polygon":[[0.10,0.35],[0.15,0.33],[0.11,0.41]]}]
    },
    "candidates": [{"horse_id":"h_7","name":"Сарана","cosine_similarity":0.91,"best_photo_id":"p_18"}]
  }]
}
```

Координаты — доли ширины и высоты оригинала от левого верхнего угла после применения ориентации фото. Полигон содержит минимум три точки по порядку обхода и замыкается при отрисовке. Число точек зависит от формы. Каждая черта хранит значение и собственный полигон или `null`, если положение неизвестно.

Для каждой детекции список особей отсортирован по максимальному косинусному сходству с одним из эталонов этой особи. Диапазон от −1 до 1. `best_photo_id` указывает на этот эталон в истории особи. `detection_confidence` относится к обнаружению лошади. Пустой `detections` означает, что на снимке лошадей не обнаружено. При пустом `candidates` можно сохранить новую особь. В рейтинг входят только подтверждённые фото с той же версией модели и размерностью эмбеддинга. При равенстве оценок выбирается эталон с меньшим `photo_id`, особи упорядочиваются по `horse_id`.

## Что Go получает от модели

При `INFER_ENGINE=yolo` и пустом `INFER_COMPARISON_URL` нода читает загруженный оригинал, применяет ориентацию JPEG и передаёт изображение встроенному движку. Для локального режима нужны сборка с CGO, библиотека ONNX Runtime (`INFER_RUNTIME_LIB`), детектор (`INFER_MODEL_PATH`) и три файла в `INFER_REID_MODEL_DIR`:

- Для эмбеддинга особи приложение скачивает `pytorch_model.bin` из версии `33b3c6f` репозитория BVRA и сохраняет как `megadescriptor-l-384.bin`. После проверки SHA-256 встроенный граф ONNX читает параметры Swin-L прямо из этого файла. Готовый экспорт `megadescriptor-l-384.onnx` также поддерживается. Зеркало `INFER_MODEL_BASE_URL` по-прежнему может раздавать этот экспорт. [Веса MegaDescriptor-L-384 и лицензия](https://huggingface.co/BVRA/MegaDescriptor-L-384/tree/33b3c6f4ee0c386a4126cc3dcd23843920613fa1).
- `dinov2-small.onnx` и `part-heads.f32` используются для сегментации и измерения видимых черт.

Нода возвращает уверенность детектора, контур маски и численные значения доступных измерений (`coat_light`, `coat_warmth`, `cheek_light`, `muzzle_contrast`, `head_ratio`). Для полигона каждой области берётся внешний контур самой большой связной части её маски. Координаты пересчитываются из рамки детекции в доли всего снимка. Пустая детекция даёт 201 с `detections: []`. Если детектор нашёл лошадь, но не удалось получить обязательную маску, нода возвращает 503. Готовые эмбеддинги из JSONL не заменяют файлы весов.

Чтобы вместо встроенного движка использовать отдельный сервис модели, задайте полный HTTP(S)-адрес в `inference.comparison_url` или `INFER_COMPARISON_URL`. Эта настройка имеет приоритет. Go отправляет исходные байты фото методом POST с MIME-типом загрузки. Сервис отвечает HTTP 200 и JSON. Координаты здесь заданы **в пикселях** изображения после применения EXIF-ориентации. Размеры кадра и все полигоны относятся к одной системе координат.

```json
{
  "model_version": "horse-seg-v1",
  "width": 1000, "height": 500,
  "detections": [{
    "detection_confidence": 0.98,
    "horse_polygon": [[100,120],[420,155],[380,395],[140,375]],
    "traits": [{"key":"muzzle","value":"light","polygon":[[100,175],[150,165],[110,205]]}],
    "embedding": [0.6,0.8]
  }]
}
```

Каждая детекция содержит эмбеддинг конкретной лошади. Go нормализует координаты по ширине и высоте, считает косинусное сходство и возвращает фронтенду готовый рейтинг. Отсутствующая маска лошади или недоступный обработчик дают 503. Некорректная геометрия, оценки или эмбеддинги дают 502. Пустой массив детекций является успешным результатом.

## История и выбор

`GET /observations?horse_id=h_7&include=photos,annotations` возвращает массив существующих записей наблюдений с дополнительными полями. Клиент открывает лучший эталон и даёт листать все фото. Один и тот же исходный файл может встречаться в наблюдениях разных лошадей со своей разметкой.

```json
[{
  "id":"obs_12","horse_id":"h_7","observed_at":"2026-11-20T09:14:00Z","observer_id":"field-3",
  "location":"У ручья","blob_ids":["<sha256>"],"name":"Сарана у ручья",
  "photos":[{
    "photo_id":"p_18","blob_sha256":"<sha256>","name":"Сарана в профиль.jpg",
    "annotation":{"horse_polygon":[[0.1,0.2],[0.7,0.3],[0.7,0.8]],"traits":[]}
  }]
}]
```

История поддерживает прежние записи только с `blob_ids`. Отсутствующая разметка соответствует `annotation: null`. Стрелки слева переключают детекцию и её кандидатов. Справа меняется только фото выбранного кандидата.

## Решение по детекции

`PUT /comparisons/cmp_42/detections/d_1/decision` принимает одно из двух тел.

| Действие | Тело |
| --- | --- |
| Существующая особь | `{"action":"match","horse_id":"h_7","observation_name":"На выпасе"}` |
| Новая особь | `{"action":"create_horse","horse_name":"Искра","observation_name":"У ручья"}` |

Успешный ответ содержит `{"observation_id":"obs_53","horse_id":"h_7","remaining_detection_ids":["d_2"]}`. Повтор того же решения возвращает ту же сохранённую запись. Попытка заменить уже принятое решение другим получает 409. Создание новой особи, наблюдения и привязка разметки одной лошади к оригиналу составляют одну операцию.

`POST /comparisons/cmp_42/cancel` без тела возвращает, например, `{"status":"cancelled","saved_observation_ids":["obs_53"],"skipped_detection_ids":["d_2"]}`. Уже подтверждённые наблюдения сохраняются. После отмены сохранение пропущенной детекции возвращает 409. При повторном подтверждении сохранённой детекции возвращаются прежние идентификаторы и актуальный остаток.

Сессия сравнения хранится на создавшей её ноде и переживает перезапуск. Подтверждение записывает наблюдение, разметку и эмбеддинг эталона в одной транзакции с событиями журнала. В качестве `observer_id` при этом используется ID ноды. Синхронизация переносит сохранённые наблюдения и эталоны на другие ноды через события, оригиналы — через существующий обмен блобами по SHA-256. Для чтения разметки и расчёта рейтинга на принимающей ноде нужна версия с этой миграцией.

В рабочем режиме клиент сообщает об отсутствующем маршруте сравнения (404/405) и недоступном обработчике или модели (501/503). Переключение на демонстрационные результаты выполняется пользователем в настройках.

## Проверка

Из каталога `backend` запустите `go test ./tests/sync_e2e -run TestComparisonAcrossNodes`. Для проверки PostgreSQL укажите `TEST_PG_DSN` тестовой БД, в которой можно создать временную схему. Второй узел использует SQLite.

Локальный путь от загрузки до ONNX проверяет `go test ./tests/sync_e2e -run '^TestLocalComparisonUpload$' -v`. Задайте `YOLO_MODEL_PATH` и `YOLO_RUNTIME_LIB` для детектора. С каталогом `INFER_REID_MODEL_DIR` эта же проверка загружает фото двух лошадей, сохраняет обеих и проверяет разметку в истории и совпадения при повторном сравнении.

Для проверки через Electron соберите ноду командой `go build -o /tmp/loshid-node ./cmd/node` в каталоге `backend`. В каталоге `app` выполните `npm run build` и `JOURNAL_NODE_BINARY=/tmp/loshid-node npm run test:go-comparison`. Для проверки упакованного клиента дополнительно задайте `JOURNAL_BINARY` с путём к исполняемому файлу Electron-приложения. Тест создаёт отдельную БД, использует тестовый HTTP-обработчик модели и проходит сравнение через рабочий интерфейс.
